1. Executive summary

This project delivers a working QR Code generator that is built the way component programming requires: the application is assembled from independent, replaceable, introspectable components rather than written as one monolithic program.

The suite contains nine components plus two infrastructure classes, every one of them a JavaBean that satisfies the mandatory bean characteristics (public class, no-argument constructor, Serializable, get/set design patterns, delegation events). The components are wired by a component registry, configured by a deployment descriptor, and consumed by three different front-end assemblies — a Swing desktop application, a command-line tool and an HTTP web service — all built from the same compiled component set.

The QR encoding itself (numeric, alphanumeric and byte modes, Reed–Solomon error correction over GF(2⁸), all eight mask patterns, versions 1–40) is implemented from ISO/IEC 18004 without any third-party dependency, and a second encoder component wraps the third-party ZXing engine behind an identical provided interface to demonstrate replaceability and interface standardisation.

Every claim in this report is backed by machine-generated evidence: the automated suite decodes each produced symbol with the independent ZXing decoder, compares the ISO/IEC 18004 parameter tables with the tables published by ZXing (160 version/level combinations, 0 mismatches), reconstructs each rendered artifact module by module, and runs negative controls that prove the checks can fail — including a corrupted-artifact control and the historical defect that the suite was designed to catch.

3. Component-oriented analysis

3.1 What component-oriented programming requires

COP builds systems by assembling pre-existing, reusable and independent components. A component is a deployable unit of software with a well-defined interface whose implementation is hidden; the classic formal definition used in the course material (Szyperski, 2002) is:

A software component is a unit of composition with contractually specified interfaces and explicit context dependencies only. A component can be deployed independently and is subject to third-party composition.

The course notes reduce this to the triple C = (I, D, B): the interfaces a component offers (I), the interfaces it requires (D), and its hidden behaviour (B). Section 4.2 lists the triple for every component of this suite; the hidden behaviour (B) lives exclusively inside the ke.ku.sco310.qr.engine package, which is deliberately package-private so that no consumer can depend on it.

3.2 Component identification and decomposition

3.5 Benefits of components realised here

  1. Faster development — the HTTP front end needed 260 lines of HTTP plumbing and no domain logic because encoding, rendering and storage already existed as components.
  2. Reliability through reuse of verified parts — the composed checks confirm that the same renderer component behaves identically in the GUI, the CLI and the web service.
  3. Standardisation — the JavaBeans conventions are what allow the BeanInspector tool (225 lines) to describe any component without knowing it in advance.
  4. Maintainability — defects are localised: the interleaving defect described in §9.4 was fixed inside one package-private method without touching any component interface.
  5. Interoperability — a symbol produced by the in-house encoder is decoded by the ZXing decoder, and vice versa (see the replaceability checks), i.e. third-party composition works in both directions.
  6. Scalability through assembly — adding a fourth renderer (for example a PDF renderer) means adding one bean and one descriptor line: no existing file changes.

3.6 Component interface incompatibility: the three classic types, and how this design avoids them

Interface incompatibility is the well-known obstacle to component reuse. The three types — and the concrete countermeasures taken in this project — are:

(1) Signature incompatibility (syntactic). The provider's method names, parameter types or exception types do not match what the consumer expects. Countermeasure: this suite freezes the contract in the ke.ku.sco310.qr.api package (QrCodeEncoder, QrCodeRenderer, QrCodeRepository, QrCodeGenerationListener) and never lets an implementation change it; the third-party ZXing engine, whose signatures are completely different (Encoder.encode(String, ErrorCorrectionLevel, Map<EncodeHintType,?>) returning a QRCode), is adapted by ZxingQrEncoderAdapterBean. Both encoders report failures through the same checked exception hierarchy, so callers need no adaptation.

(2) Protocol / behavioural incompatibility (interaction order and state). Even with matching signatures, components may disagree about the sequence of calls, blocking behaviour or state expectations. Countermeasure: the doc-comments of every interface state pre-conditions and post-conditions (for example "render accepts a non-null symbol produced by an encoder of this suite and returns a non-empty artifact whose format matches getFormatName()"), and the facade enforces the generation order encode → render → store → notify. The listener contract is one-directional and non-blocking, and the facade isolates a misbehaving listener with a try/catch so that a faulty listener cannot break the generation protocol.

(3) Semantic / quality-of-service incompatibility (meaning of data). Components may agree on syntax and protocol yet disagree on what the data means: units, colour space, coordinate origin or quality guarantees. Countermeasure: the suite publishes semantics in metadata and keeps the value object explicit — a QrCode always states its version, size, mask, error-correction level and module matrix indexed [y][x] with true meaning dark; a RenderedArtifact always declares formatName, fileExtension, mimeType and pixel dimensions so that consumers do not have to guess; the PNG renderer documents that the quiet zone is painted with the background colour and that module centres can be sampled at (quietZone + x) * moduleSize + moduleSize/2 (this is exactly how the test suite verifies it). Capability metadata (EncoderInfo) states the supported modes and version range, so a consumer can test admissibility before calling.

A related, subtler problem is capability and context mismatch: the ZXing adapter declares requiresOptionalLibrary = true and ComponentRegistry asks OptionalComponentSupport.isZxingAvailable() before instantiating it, so a missing library degrades the deployment (the in-house engine stays wired) instead of producing a NoClassDefFoundError at the first call — explicit context dependencies in practice.

4.4 The deployment model

Packaging follows steps 4–6 of the bean recipe:

  • manifest/MANIFEST.MF — declares Main-Class, Class-Path, specification metadata for the JavaBeans component model and a Java-Bean: True block for every bean class file;
  • out/dist/qr-component-suite-1.0.0.jar — the deployable unit (122 KB, 52 classes, 53 entries) plus lib/ for the optional ZXing component;
  • config/assembly.xml — the deployment descriptor: component selection per role and the design-time values of their properties. Deployments change by editing this file, never by recompiling, which is exactly the parameter set P of the deployment quadruple D = (C, E, P, L) used in the course material (C = the component set, E = Java SE 11+, P = the descriptor, L = the machine/workspace).

4.5 Persistence: two mechanisms, as the course requires

  1. Serialization. FileSystemRepositoryBean serialises the list of QrHistoryEntry records into history.ser (ObjectOutputStream) and reads it back with ObjectInputStream; the records themselves implement Serializable with a no-argument constructor. Verified by "reinstantiating the repository component reads the same history file".
  2. XML bean persistence. BeanPersistence uses java.beans.XMLEncoder/XMLDecoder to write and rebuild the whole assembled bean graph — class names, property values and wiring: docs/evidence/work/bean-graph.xml (1.2 KB). This is the mechanism the original Bean Builder used, and it is verified by "the assembled bean graph survives an XML round trip" and "the restored assembly can generate without recompiling". Properties that would bloat the file are excluded declaratively through a BeanInfo (QrHistoryBeanBeanInfo marks the indexed history property transient for the encoder) — a technique the course notes call "expose only those features you want to expose".

7. The encoding logic, in detail

This chapter explains the logic that the encoder components hide behind QrCodeEncoder. Everything described here lives in the package-private ke.ku.sco310.qr.engine package, and every number quoted was produced by running the compiled code (the worked examples come from instrumentation of the real engine (ke.ku.sco310.qr.test.MaskComparisonTool), and the tables are cross-checked against ZXing in docs/evidence/table-cross-check.csv).

7.1 The five pipeline stages

QrEngine.encode(...) is organised exactly like clause 8 of ISO/IEC 18004:

Stage Clause Method What it decides
1. Data analysis 8.3–8.4 QrSegment.makeSegments which encoding mode is most compact for the payload
2. Data encoding 8.4 QrSegment.makeNumeric/Alphanumeric/Bytes the bit stream of the payload
3. Error correction 8.5 ReedSolomon.computeRemainder one Reed–Solomon block per interleaving block
4. Structure finalisation 8.6 QrEngine.addEccAndInterleave block split and codeword interleaving
5. Module placement 8.7–8.9 drawFunctionPatterns, drawCodewords, applyMask, drawFormatBits, drawVersionBits the final matrix, including the mask

7.2 Stage 1–2: mode analysis and bit-level encoding

The payload chooses its mode by inspection — the most compact representation wins:

Mode Indicator Character set Payload bits Character-count bits (v1–9 / v10–26 / v27–40)
Numeric 0001 0-9 3 digits → 10 bits, 2 → 7 bits, 1 → 4 bits 10 / 12 / 14
Alphanumeric 0010 0-9 A-Z $ % * + - . / : space (45 symbols) 2 chars → 11 bits, 1 → 6 bits 9 / 11 / 13
Byte 0100 arbitrary data (UTF-8 in this suite) 8 bits per byte 8 / 16 / 16

The character-count widths are declared as data on the enum, so a table error would be visible in one place:

NUMERIC(0x1, new int[]{10, 12, 14}),
ALPHANUMERIC(0x2, new int[]{9, 11, 13}),
BYTE(0x4, new int[]{8, 16, 16});

Two details are easy to get wrong and are called out here because the project's own test suite caught one of them (see §9.4):

  • the byte-mode counter is 8 bits for versions 1–9 but 16 bits for versions 10–40, which is why the reported maximum capacity is 2 953 bytes at level L (version 40) and not 2 956;
  • numeric groups are padded to the left with zeros — Integer.parseInt("012") is 12, encoded in the 10 bits 0000001100.

Mode selection is proven by three checks and by a capacity comparison:

PASS numeric payload selects numeric mode        expected=Numeric actual=Numeric
PASS upper-case payload selects alphanumeric     expected=Alphanumeric actual=Alphanumeric
PASS mixed case payload selects byte mode        expected=Byte actual=Byte
PASS compact mode lowers the symbol version      numeric v1 vs alphanumeric v1

7.3 Stage 3: version selection

The version is chosen by the smallest symbol whose data capacity, in bits, can hold the whole bit stream (mode indicator + character count + payload, plus the terminator). Capacity comes from QrTables.numDataCodewords(version, level) · 8, so it always matches the table used for the error-correction blocks:

while (true) {
    usedBits = totalBits(segments, version);
    int capacityBits = QrTables.numDataCodewords(version, level) * 8;
    if (usedBits <= capacityBits) break;
    if (version >= maximumVersion) throw new QrEncodingException(producerId, ...);
    version++;
}

If boostErrorCorrection is set, the level is then raised as far as the same symbol still allows — a robustness increase that costs no extra modules. If the payload does not fit even at version 40, the component fails with a message that names the requirement and the capacity:

Payload of 200 characters does not fit version 1 at level H
(needs 1113 bits, capacity 72 bits). Shorten the payload or lower the error-correction level.

The capacity model is validated exhaustively: for all 160 version/level combinations the encoder is given the largest byte payload that fits and the produced symbol is decoded again — 160 decoded, 0 failed (docs/evidence/capacity-matrix.csv).

7.5 Stage 3: Reed–Solomon over GF(2⁸)

Error correction is the part of QR encoding that most implementations get subtly wrong, so the implementation is deliberately explicit. GaloisField builds the log/antilog tables for the field generated by the primitive polynomial x⁸ + x⁴ + x³ + x² + 1 (0x11D) once, in a static initialiser:

int x = 1;
for (int i = 0; i < 255; i++) {
    EXP[i] = x;  LOG[x] = i;
    x <<= 1;
    if ((x & 0x100) != 0) x ^= 0x11D;    // reduce modulo the primitive polynomial
}

Multiplication is then a logarithm addition, EXP[LOG[a] + LOG[b]], with the 512-entry EXP table making the doubling of the table unnecessary.

ReedSolomon.computeDivisor(degree) builds the generator polynomial (x − α⁰)(x − α¹)…(x − α^(degree−1)); computeRemainder(data, degree) performs the polynomial division with a degree-byte shift register:

for (byte b : data) {
    int factor = (b & 0xFF) ^ remainder[0];
    System.arraycopy(remainder, 1, remainder, 0, degree - 1);
    remainder[degree - 1] = 0;
    for (int i = 0; i < degree; i++) remainder[i] ^= GaloisField.multiply(divisor[i], factor);
}

The remainder is the sequence of error-correction codewords. The register already performs the x^degree shift, so feeding only the data codewords is correct — feeding zero-padded placeholders as well is the defect documented in §9.4.

7.6 Stage 4b: block splitting and interleaving

For versions and levels where a symbol has more than one block, the data codewords are split into numErrorCorrectionBlocks blocks and the ECC codewords of each block are interleaved with the data codewords. The implementation follows clause 8.6 literally, and the two phases are deliberately kept apart:

phase 1: for column = 0 … maxDataLen-1:  for block = 0 … n-1: emit block[column]
phase 2: for column = 0 … blockEccLen-1: for block = 0 … n-1: emit blockEcc[column]

Blocks are "short" (shortBlockLen) or "long" (shortBlockLen + 1), and the short blocks contribute no codeword at all in the last data column. Interleaving naively — walking data and ECC columns together — produces a matrix that looks plausible but decodes to garbage; the automated suite caught precisely that during development (§9.4, defect 1).

The block arithmetic is stated once and used everywhere:

int numBlocks      = QrTables.numErrorCorrectionBlocks(level, version);
int blockEccLen    = QrTables.eccCodewordsPerBlock(level, version);
int rawCodewords   = QrTables.totalCodewords(version);
int shortBlockLen  = rawCodewords / numBlocks;
int numShortBlocks = numBlocks - rawCodewords % numBlocks;

7.7 Stage 5a: function patterns

Before any data module is placed, the reserved patterns are drawn and flagged in a parallel isFunction matrix so that later stages can never overwrite them:

Pattern Position Source
Finder patterns + separators (3,3), (size−4,3), (3,size−4) drawn by drawFinderPattern, 7×7 with a light separator
Timing patterns row 6 and column 6 alternating dark/light, drawFunctionPatterns
Alignment patterns QrTables.alignmentPatternPositions(version) 5×5 patterns excluding the three finder corners
Dark module (8, size−8) always dark, written with the format information
Format information around the two finder patterns 15 bits, BCH(15,5)-protected
Version information two 6×3 blocks, version ≥ 7 18 bits, BCH(18,6)-protected

7.8 Stage 5b: codeword placement

The final codewords are placed in the two-module-wide zig-zag order of clause 8.7: columns are visited in pairs from right to left, skipping the vertical timing column (6), and alternating upward and downward. Only non-function modules receive bits:

for (int right = size - 1; right >= 1; right -= 2) {
    if (right == 6) right = 5;
    for (int vert = 0; vert < size; vert++) {
        for (int j = 0; j < 2; j++) {
            int x = right - j;
            boolean upward = ((right + 1) & 2) == 0;
            int y = upward ? size - 1 - vert : vert;
            if (!isFunction[y][x] && i < data.length * 8) {
                modules[y][x] = getBit(data[i >>> 3], 7 - (i & 7));
                i++;
            }
        }
    }
}

7.9 Stage 5c: mask selection and the penalty function

All eight mask patterns of the standard are implemented as the specification's formulas:

Mask Condition to invert (x, y) Row/column it favours
0 (x + y) % 2 == 0 checkerboard
1 y % 2 == 0 horizontal stripes
2 x % 3 == 0 vertical stripes
3 (x + y) % 3 == 0 diagonal
4 (x/3 + y/2) % 2 == 0 large blocks
5 x·y % 2 + x·y % 3 == 0 dense
6 (x·y % 2 + x·y % 3) % 2 == 0 dense, mixed
7 ((x + y) % 2 + x·y % 3) % 2 == 0 dense, mixed

The best mask is the one with the lowest penalty, scored by the four rules of clause 8.8.2 with weights N1 = 3, N2 = 3, N3 = 40, N4 = 10:

Rule Penalty
1 — a run of 5+ modules of the same colour 3 + (runLength − 5)
2 — every 2×2 block of the same colour 3
3 — a 1:1:3:1:1 finder-like pattern with four light modules on one side 40
4 — deviation of the dark-module ratio from 50 % 10 · k, where k is the number of 5 % steps outside the target

The engine evaluates each candidate, writes the corresponding format bits, scores the matrix, then undid the candidate (XOR is its own inverse) before trying the next:

for (int candidate = 0; candidate < 8; candidate++) {
    engine.applyMask(candidate);
    engine.drawFormatBits(candidate, level);
    int penalty = engine.getPenaltyScore();
    if (penalty < bestPenalty) { bestPenalty = penalty; mask = candidate; }
    engine.applyMask(candidate);            // undo
}

Penalty scores are observable in the report instead of plausible:

payload 01234567  v1-M   mask 0   penalty 1057       (the chosen mask)
                         mask 1   penalty 1253
                         mask 2   penalty 1117   …   mask 7 penalty 1126

Because rule 3 leaves room for interpretation at the symbol border (the standard's Figure 24 amendment treats the surrounding quiet zone as light modules), a different implementation can pick a different mask for the same payload. §9.6 quantifies that divergence honestly rather than pretending the implementations are bit-identical.

7.10 Format and version information

The 15-bit format field carries the 2-bit error-correction indicator (the formatBits value of QrErrorCorrection: L = 01, M = 00, Q = 11, H = 10) and the 3-bit mask number, protected by a BCH(15,5) code and finally XOR-ed with the constant 0x5412:

int data = level.getFormatBits() << 3 | mask;
int rem = data;
for (int i = 0; i < 10; i++) rem = (rem << 1) ^ ((rem >>> 9) * 0x537);
int bits = (data << 10 | rem) ^ 0x5412;

Versions ≥ 7 additionally carry an 18-bit version field, generated with the generator polynomial 0x1F25 and placed in two 6×3 blocks. Both fields are written into the isFunction matrix, so data placement can never collide with them.

Note the deliberate design of the level enum: the declaration order (L, M, Q, H) matches the row order of the error-correction tables, so ECC_CODEWORDS_PER_BLOCK[ecl.ordinal()][version] is the whole indexing scheme — one fewer chance of an off-by-one error.

PNG pixelSize = (size + 2·quietZone) · moduleSize; dark modules are drawn as horizontal runs with fillRect every pixel of all 1 089 modules of a v5 symbol is sampled and compared: 0 of 1089 modules mismatched
SVG one <rect> per module, or one per run when mergeHorizontalRuns is on; width/height in millimetres when physicalWidthMillimetres is set the document is parsed back into a matrix: 0 module mismatches, and the element count halves (297 vs 577)
ASCII two glyphs per module with a configurable border the text is parsed back into a matrix: 0 module mismatches

The ASCII renderer's glyph default (██ for dark, two spaces for light) is the aspect-ratio correction that makes a text symbol square in a terminal whose character cell is about twice as tall as it is wide.

9. Verification: how the claims in this report were tested

A component suite is only as good as the evidence that it works. This chapter describes the verification strategy, the results, the defects the strategy caught, and — importantly — the two places where this implementation legitimately differs from another conforming implementation.

9.1 Strategy

Four independent techniques are used, because each one catches a different class of error:

Technique What it catches Where it is used
Independent oracle an error in our own tables or encoding logic every produced symbol is decoded by ZXing, a completely separate implementation; the 160 ISO/IEC 18004 parameter combinations are compared cell by cell with ZXing's tables
Round-trip / reconstruction errors in placement, masking, rendering or persistence payload → symbol → PNG/SVG/ASCII → parse back → matrix → decode → payload must return unchanged
Exhaustive sweeps boundary errors that a single example misses all 40 versions × 4 levels: 160 capacity cases, 160 table comparisons, 8 forced masks, 60 payload×level decodes
Negative controls a test that passes for the wrong reason inputs that must fail are asserted to fail, with the exact exception and message; one artifact is deliberately corrupted to prove the decoder really rejects it

9.4 Defect log — what the verification caught

These are the real defects found while building and verifying the suite. They are documented because they show the difference the evidence made: three of them would have shipped as silently wrong QR codes.

Defect 1 — Reed–Solomon input and interleaving order (critical). The first implementation fed the shift register data + zero-padded ECC placeholders instead of just the data codewords, and interleaved the codewords column-by-column across the combined data and ECC sequence. The generated matrices looked like QR codes and passed a naive "is it 21×21 with three finder patterns" check, but no decoder could read them. Cause the register in a polynomial-division implementation already performs the x^degree shift, so the placeholders are a double shift. Fix ReedSolomon.computeRemainder(dataPart, blockEccLen) with the data part only, and a two-phase interleave (all data columns, then all ECC columns), with short blocks contributing nothing in the last data column. Regression test PASS payloads survive the ZXing decode round trip (60 decoded, 0 failed) and the 160-case capacity sweep — neither can pass with this bug present.

Defect 2 — byte-mode character-count width for versions 10–40 (high). The character-count field was hard-coded to 8 bits for byte mode. The standard specifies 8 bits for versions 1–9 but 16 bits for versions 10–40. Symptom symbols from version 10 upward decoded to garbage or failed to decode at all; capacity for those versions was reported 8 bits too high. Fix the width is now data on QrEncodingMode (new int[]{8, 16, 16}) and byteCapacity(...) derives the maximum payload from it, so the reported maximum at level L is exactly the specification's 2 953 bytes. Regression test PASS maximum byte capacity reported for level L — expected=2953 actual=2953 plus the 160-case capacity matrix.

Defect 3 — numeric mode bit widths (medium). Three-digit numeric groups were emitted in 11 bits instead of 10, and singleton groups in 5 bits instead of 4. Symptom numeric payloads were one bit per group too long, which could push a payload into a larger version than necessary, and made the stream unreadable to a conforming decoder once the error was not compensated. Fix take == 3 ? 10 : (take == 2 ? 7 : 4). Regression test PASS numeric payload selects numeric mode, PASS compact mode lowers the symbol version, and the numeric entries of the 60-case decode sweep.

Defect 4 — the screenshot path blocked the Swing event dispatch thread (medium). QrStudioGuiAssembly --screenshot did its work inside SwingUtilities.invokeAndWait(...) and then called Thread.sleep(400) inside that block to let the layout settle. Sleeping on the event dispatch thread forbids the queued re-layout and repaint events from running, so the captured window was painted with the pre-generation layout — the symbol identity label was still sized for the placeholder text - and was therefore rendered as .... Fix three phases: build and generate on the EDT, wait off the EDT, then paint on the EDT again. Effect the symbol metadata now appears correctly in the status bar of docs/screenshots/03-gui-png-assembly.png (v7-M mask 2 Byte 45x45).

Defect 5 — property sheet collapsed and preview cropped (medium, presentation). Two layout defects in the desktop assembly: GridBagLayout centres its grid when the container is taller than its content, so the property sheet floated in the middle of the window; and the artifact preview was placed in a scroll pane that clipped large symbols (a version-7 symbol at 10 px per module is 450 px wide). Fix the property sheet is hosted in the NORTH slot of a BorderLayout so it stays anchored; the payload and colour rows received explicit minimum sizes as well as preferred sizes (GridBagLayout honours the minimum when it arranges a grid that would otherwise overflow); and the preview is now a card-switching panel whose raster card paints the artifact scaled to fit with nearest-neighbour interpolation, never enlarged above 1:1 so that module edges stay exact.

Defect 6 — the indexed property was invisible to introspection (high, course requirement). QrHistoryBeanBeanInfo declared entries with a plain PropertyDescriptor so that the property could be marked transient for XMLEncoder. A side effect of an explicit BeanInfo is that the introspector no longer derives the automatic IndexedPropertyDescriptor, so getEntries(int) / setEntries(int, …) and the indexed property-change events disappeared from the bean's feature set. The bean had an indexed property, but the project could not demonstrate one — and "the four kinds of properties" is an explicit requirement of the component model. Fix new IndexedPropertyDescriptor("entries", QrHistoryBean.class), keeping the transient flag. The tool now reports the property as indexed on the compiled class:

PROPERTY       TYPE                 READ   WRITE  INDEXED   CATEGORY  PROPERTY EDITOR
entries        QrHistoryEntry[]     yes    yes    yes       normal    -

Defect 7 — 15 compiler warnings (low, hygiene). -Xlint:all reported 15 serialisation warnings because the beans declared mutable properties without a serialVersionUID. Fix every bean declares private static final long serialVersionUID = 1L; (and the support objects that are serialised alongside it). The build now compiles with zero warnings, which is what makes the count of warnings = 0 claim in §10 verifiable.

9.6 Known divergences from another conforming implementation

Good engineering states its limits. Two differences from ZXing were found, characterised and recorded in docs/evidence/mask-selection-comparison.csv (104 payload/level pairs):

Difference Measurement Explanation
Mask pattern chosen identical in 67 of 100 cases where the symbol version agrees penalty rule 3 ("1:1:3:1:1" finder-like patterns) is interpreted differently at the symbol border: this implementation treats the surrounding quiet zone as light modules, while ZXing does not consider the border. Both symbols are conformant — the decoder reads the mask from the format information — and both decode.
Symbol version for non-Latin payloads identical in 100 of 104 cases ZXing's encoder defaults to ISO-8859-1 and therefore replaces characters it cannot represent with ?, which makes its symbols smaller for CJK text but lossy. This suite emits the payload's UTF-8 bytes, which preserves the data (verified by decoding back CJK and emoji payloads) at the cost of one or two extra versions.

Neither difference affects decodability: all 104 symbols in the comparison decode, and the produced symbols for the 160 capacity cases and the 60 round-trip payloads all decode exactly. Recording the divergence is the honest alternative to claiming bit-for-bit equality with another implementation — and the "different but still conformant" framing is itself part of the component-programming story: two interchangeable implementations of one interface need not be identical, only contract-equivalent.

10.5 Conclusion

The project set out to show that a QR Code generator can be assembled rather than written, and the result demonstrates the claim on four levels.

Architecturally, the suite is nine JavaBeans components plus two infrastructure classes. Each has a published interface, a declared set of dependencies, and behaviour that no consumer can reach into. The only place where QR-specific complexity lives is a package-private engine package, which is exactly what the component triple C = (I, D, B) asks for.

Practically, the same compiled components serve a desktop GUI, a command-line tool and an HTTP service, and the renderer or the entire encoder can be replaced at run time by editing an XML descriptor or by calling one setter — with the assembly tests proving that a swapped component still produces the same symbol.

Technically, the encoder is a complete, dependency-free implementation of ISO/IEC 18004, and it is verifiable rather than merely plausible: the data and error-correction codewords reproduce the worked example published in the standard byte for byte, all 160 version/level capacities produce decodable symbols, and all 60 round-trip payloads come back exactly, including accented text, CJK and emoji.

Methodologically, the project is honest about its evidence. The verification suite is designed so that its checks are capable of failing — proven by deliberately corrupted artifacts and by the seven defects it actually caught during development — and the two places where this implementation legitimately differs from ZXing are measured, explained and recorded instead of being hidden.

Appendix C — Course questions answered from this project

The unit's past papers ask a small number of recurring questions. Each is answered below using this project as the example, which is the shortest route from the theory in the notes to a concrete, checkable answer.

Q1. "An air-conditioning system is a component-based system." Discuss. A component-based system is one whose functionality is delivered by independent, replaceable units that communicate through interfaces. An air-conditioning installation fits this description exactly, and it maps onto this project one role at a time: a sensor component provides a readTemperature() interface (our QrCodeEncoder.encode()); a controller component requires that interface and provides setTarget() (our QrStudioFacadeBean, which requires four interfaces); an actuator/compressor component consumes commands and provides cooling (our PngRendererBean); a display and a logger are listeners on the controller's events (our AuditLogListenerBean). The system is component based rather than merely modular because units can be replaced without redesign: swapping a mercury thermostat for a digital sensor changes one component, not the system, exactly as swapping renderer.png.v1 for renderer.svg.v1 changes the output format without touching the encoder, the facade or either front end. The formal definition from the notes — contractually specified interfaces, explicit context dependencies, independent deployment, third-party composition — is satisfied by both.

Q2. "Describe the three types of component interface incompatibility." Signature incompatibility — the names, parameter types or return types of an operation do not match (play(File) versus play(String)). Protocol or behavioural incompatibility — the signatures match, but the expected sequence of calls, the blocking behaviour or the error contract differs (a component that requires open(); use(); close(); versus one that expects a single process(); or one that signals failure by exception versus by return code). Semantic or quality incompatibility — the operation succeeds but the meaning or quality of the result differs (both components claim to "encode a QR code", but one supports only byte mode, or only versions 1–9, or targets a different error-correction level). This project avoids all three deliberately. Signature incompatibility is avoided because the implementations share one interface (QrCodeEncoder) and the third-party library is adapted, never called directly. Protocol incompatibility is avoided because the interaction contract is published as a Javadoc pre/post-condition block on each interface method and is asserted by the test suite. Semantic incompatibility is avoided by making capability metadata part of the provided interface: getEncoderInfo() returns versions, modes, maximum capacity and a thirdParty flag, so a caller can discover that a component is only "equivalent in interface, not in capability" before using it — which is precisely what ComponentRegistry does when it reports a component as unavailable rather than silently substituting it.

Q3. "How is component-based software engineering different from object-oriented programming?" OOP decomposes a solution into classes and objects and reuses them by inheritance, composition and polymorphism; the unit of reuse is the class and the decision is made at compile time. CBSE decomposes a solution into deployable components with contractually specified interfaces; the unit of reuse is the binary component, the dependencies are declared rather than implicit, and the decision is made at deployment or run time by an assembler. In this project the same code base demonstrates both: QrCode, BitBuffer and GaloisField are ordinary OOP objects inside the component, while the reused artefact is PureJavaQrEncoderBean, deployed into three different front ends by editing one XML file.

Q4. "Outline the steps to create a JavaBean." (1) a public class; (2) a public no-argument constructor; (3) properties exposed through get/set methods; (4) Serializable for persistence; (5) event delegation through add/remove<Listener> methods; (6) optional BeanInfo classes for builder tools; (7) packaging with a manifest that marks the classes as beans (Java-Bean: True); (8) testing through introspection. §4.1 of this report tabulates each step against the class that implements it, and java -cp out/classes:lib/* ke.ku.sco310.qr.cli.QrCliAssembly --inspect <class> demonstrates steps 3–6 and 8 on the compiled bytecode.
